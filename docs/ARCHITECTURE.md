# Архитектура

Документ описывает, как устроен проект и почему он устроен именно так.

---

## Главное решение: ядро без ввода-вывода

Всё, что относится к правилам игры, лежит в `engine/` и не делает ни одного вызова
ввода-вывода. Ни `printf`, ни чтения клавиш, ни работы с файлами. Наружу торчит один класс:

```cpp
class Game {
public:
    void start(const GameConfig& cfg);
    bool perform(const Action& action);   // true, если ход был потрачен

    const Map& map() const;
    const Hero& hero() const;
    const std::vector<Monster>& monsters() const;
    const std::vector<LogEntry>& log() const;
    RenderCell render_at(Vec2 p) const;

    std::string save() const;
    bool load(const std::string& blob);
};
```

Фронтенд присылает `Action` и читает состояние обратно. Больше между ними ничего нет.

Из этого следуют три вещи, ради которых всё и затевалось:

1. **Правила проверяются тестами без экрана.** Тест создаёт `Game`, ставит героя куда нужно,
   выдаёт `Action` и смотрит на результат. Никаких моков терминала.
2. **Два фронтенда работают с одним кодом.** Терминальная версия и версия для браузера — это
   два разных способа нарисовать одно и то же состояние и превратить нажатие в `Action`.
3. **Сохранение — это сериализация состояния, а не отдельная подсистема.** Всё, что описывает
   партию, уже собрано в одном объекте.

```
                    ┌─────────────────────────────────┐
                    │            engine/              │
                    │                                 │
   Action ────────► │   Game::perform()               │
                    │     ├─ actions.cpp   ход героя  │
                    │     ├─ ai.cpp        ход тварей │
                    │     ├─ game.cpp      очередь    │
                    │     ├─ mapgen.cpp    генерация  │
                    │     ├─ fov.cpp       обзор      │
                    │     ├─ pathfind.cpp  A* и поток │
                    │     ├─ data.cpp      контент    │
                    │     └─ save.cpp      сохранения │
                    │                                 │
   состояние ◄───── │   map() hero() monsters() ...   │
                    └─────────────────────────────────┘
                        ▲             ▲             ▲
                        │             │             │
              ┌─────────┴───┐  ┌──────┴──────┐  ┌───┴──────┐
              │  терминал   │  │   браузер   │  │  тесты   │
              │  ANSI+termios│ │  WASM+canvas│  │GoogleTest│
              └─────────────┘  └─────────────┘  └──────────┘
```

| `game.cpp` | Жизненный цикл, этажи, очередь ходов, производные характеристики |

| `save.cpp` | Сериализация и строгая загрузка |

| `achievements.cpp` | Достижения и их прогресс между запусками |

Весь контент собран в одном `data.cpp` намеренно: баланс игры видно в одном диффе, а код
правил остаётся свободным от магических чисел.

## Ключевые решения и их причины

### Свой генератор случайных чисел

`std::mt19937` переносим, но `std::uniform_int_distribution` — нет: одна и та же
последовательность даёт разные числа в libstdc++, libc++ и MSVC. Для игры, где зерно должно
задавать подземелье одинаково на всех платформах и в браузере, это неприемлемо.

Используется xoshiro256\*\* с посевом через splitmix64 и выборкой с отбраковкой (rejection
sampling), чтобы распределение было ровно равномерным, а не смещённым, как при `% n`.
Состояние генератора входит в сохранение — иначе загруженная партия разошлась бы с исходной.

Своего генератора мало: собственный код тоже умеет разойтись между платформами, и молча.
`build_arena` сортировал кандидатов в дверь по расстоянию до входа, не доопределяя порядок
среди равных, — а дальше брал первого прошедшего проверку связности. `std::sort` порядок
равных не определяет, и он действительно разный в libstdc++, libc++ и MSVC; на обходе всего
подземелья совпадения нашлись у 18 залов из 26. То есть одно зерно давало разные подземелья,
и заметить это было нечем: все тесты на детерминизм сравнивали два прогона внутри одного
процесса, где стандартная библиотека одна и та же.

Поэтому в `tests/test_portability.cpp` лежат отпечатки — FNV-1a по тайлам, лестницам, залам,
монстрам и предметам всех шестнадцати этажей для трёх фиксированных зёрен, записанные в
репозиторий. Матрица CI из четырёх платформ сравнивает теперь GCC с Clang, с MSVC и с
Emscripten, а не каждого с самим собой. Отпечатков два — отдельно рельеф и отдельно
содержимое: правка баланса двигает всех монстров на всех этажах и не должна обесценивать
канарейку по рельефу, иначе её перестанут читать. FNV написан руками, а не взят из
`std::hash`: последний вправе отличаться между реализациями и сигналил бы ровно по той оси,
которую должен сторожить.

### Очередь ходов по энергии

У каждого существа есть скорость и накопленная энергия. За такт все получают энергию, равную
своей скорости, и действуют, пока её хватает на ход (100 единиц). Витязь со скоростью 100
ходит раз за такт, Волколак со скоростью 130 — примерно 1,3 раза, а Каменная баба со
скоростью 70 — 0,7.

Это даёт бесплатно: эффекты ускорения и замедления, разную стоимость действий (вода стоит
полтора хода) и возможность оглушить существо, просто не дав ему потратить энергию.

Цикл ограничен сверху: если бы планировщик когда-нибудь зациклился, это проявится как
падающий тест, а не как зависшая вкладка браузера.

### Четыре пояса — четыре мира

Подземелье разбито на четыре пояса по четыре этажа: Погост (1–4), Чернотопь (5–8), Кощеево
царство (9–12), Пекло (13–16). Пояс — это не число, а строчка в таблице `ZoneTheme`:

```cpp
struct ZoneTheme {
    Zone zone;
    Text name, arrival;
    const char* wall_color; const char* floor_color; const char* liquid_color;
    bool caves;            // пещеры вместо комнат
    int water_chance, chasm_chance, door_chance, extra_monsters;
};
```

Из таблицы читают ровно два места: `ensure_level()` заполняет по ней настройки генератора, а
`render_at()` берёт цвета. Больше про пояса не знает никто — новый пояс добавляется одной
строкой в таблицу и одной веткой в `zone_for_depth()`.

Почему пояса вообще появились: до них этажи резались одним алгоритмом в одной палитре, и спуск
ощущался как повторение. Границы поставлены по боссам, поэтому каждый страж получает свой мир,
а не просто комнату побольше.

В каждом поясе стражей двое: меньший на середине (этажи 3, 7, 11, 15) и хозяин на дне
(4, 8, 12, 16) — всего восемь. Четыре этажа подряд без единого боя, оканчивающиеся одной
дракой, читались как коридор с дверью в конце; бой на середине разбивает пояс надвое. Меньший
страж помечен `AiMiniBoss` и, в отличие от хозяина, зала не получает — от него можно уйти, и
почти вся разница между «меньший» и «хозяин» именно в этом.

### Две генерации вместо одной

Пещеры Чернотопи строит клеточный автомат: случайная заливка 48% стенами, затем четыре прохода
сглаживания по правилу «стена, если вокруг ≥5 стен».

Первые два прохода дополнительно превращают в стену клетки, у которых стен вокруг **не больше
одной**. Без этого правила автомат вылизывает уровень в одну сплошную пещеру на 79% площади:
играбельно, но прятаться негде и смотреть не на что. С ним остаются столбы и ниши, и открытая
площадь падает до разумных 60%.

Связность решается иначе, чем в комнатах. Ремонт туннелями здесь не годится: прямой прорубленный
коридор посреди пещеры выглядит ровно тем, чем является — заплаткой. Вместо этого находится
самая большая связная область, а всё остальное заливается обратно стеной. Получается одна
пещера, связная по построению. Лестницы ставятся в её концы двумя проходами «найди самую
далёкую клетку» — тем же приёмом, которым ищут диаметр дерева.

### Механики боссов

Босс, у которого больше здоровья и больше урон, — это не босс, а стена. Каждый из восьми
работает на механике из первоисточника, и у каждой есть контригра:

| Страж | Этаж | Механика | Ответ игрока |
|---|---|---|---|
| Мара | 3 | На расстоянии наводит морок; со второй фазы ещё и двоится | Подойти вплотную |
| **Вий** | 4 | Веки опущены (и он получает +50% урона), затем поднимает их и бьёт всё, что видит | Уйти с линии взгляда по предупреждению |
| Водяной | 7 | Лечится, стоя в воде; со второй фазы затапливает пол вокруг себя | Не дать увести бой в воду |
| **Баба-Яга** | 8 | Пока стоит хоть одна изба, урон по ней делится на пять, а она отступает и зовёт подмогу | Сначала снести избы |
| Морозко | 11 | Копит дыхание и бьёт стужей, замораживая на ход-два | Не стоять на месте к концу отсчёта |
| **Кощей** | 12 | Сбитый до нуля, воскресает с 60% здоровья | Найти и сломать иглу на том же этаже |
| Полоз | 15 | Обжигает вблизи; со второй фазы уходит в камень и выходит рядом с героем | Дистанция перестаёт быть защитой — бить, а не кайтить |
| **Горыныч** | 16 | Дышит огнём по линии тем чаще, чем меньше голов осталось | Разрывать линию, добивать быстро |

Жирным выделены хозяева поясов — те, кому строится зал. Остальные четверо помечены
`AiMiniBoss`: их можно обойти.

Технически всё это — одна функция `boss_turn()`, вызываемая до обычного поведения и
возвращающая «ход потрачен», плюс несколько ветвей в `damage_monster()`. Состояние боссов — два
поля в `Monster` (`charge` — отсчёт телеграфа, `revives` — воскрешения Кощея и, отдельной
защёлкой, третья фаза Бабы-Яги) и один флаг в `Game` (сломана ли игла), и всё это входит в
сохранение.

Ветвление идёт по строковому ключу существа, а не по перечислению: ключ и так есть, он же
уходит во фронтенд именем спрайта, и лишний enum пришлось бы держать в согласии с таблицей
руками. Плата за это — правило и таблица, которые могут разойтись молча, поэтому ключи, на
которых висит поведение, объявлены один раз в `species_key`/`gear_key` (`data.hpp`) и
проверяются тестом `GameData.EveryBehaviourKeyNamesSomething`. Переименованный в таблице
страж теперь роняет тест, а не тихо теряет свою способность.

Отдельное правило: **механика, о которой нельзя догадаться, — это не загадка, а издевательство.**
Поэтому Вий предупреждает за ход, падение последней избы объявляется отдельным сообщением, а
первое воскрешение Кощея открывает карту этажа целиком, чтобы иглу было где искать.

### Классы: механика вместо разброса характеристик

Три первых класса отличаются числами. Три добавленных позже — поведением, и это оказалось
куда важнее для ощущения:

```cpp
enum ClassTrait : std::uint32_t {
    TraitHerbalist = 1u << 0,  // знает все зелья, и они крепче
    TraitSmith     = 1u << 1,  // снаряжение на ступень лучше, капища вполовину
    TraitCleave    = 1u << 2,  // удар достаёт всех соседей
};
```

Флаг лежит в `ClassTemplate`, а проверяется через `class_has()` там, где правило и живёт:
травничество в `quaff()`, кузнечное дело в `hero_attack()`/`hero_defence()` и `act_pray()`,
размах в `hero_attacks()`. Нигде нет `switch` по классу — добавить класс значит добавить строку
в таблицу и, если нужно, один флаг.

### Генерация этажа с гарантией связности

1. Уровень рекурсивно режется BSP-разбиением на области.
2. В каждом листе вырезается комната случайного размера.
3. Каждый внутренний узел соединяет комнату из левого поддерева с комнатой из правого —
   по построению получается остовное дерево над всеми комнатами.
4. Добавляется несколько лишних коридоров, чтобы этаж не был чистым деревом из тупиков.
5. **Проход ремонта связности**: заливкой ищутся отрезанные области, и к ближайшей достижимой
   клетке пробивается туннель. Цикл ограничен числом областей, поэтому всегда завершается.
6. Расставляются вода, пропасти, двери, капище и лестницы. Пропасти непроходимы, поэтому после
   них ремонт запускается ещё раз.

Пункт 5 существует потому, что шаги 2–4 не дают гарантии сами по себе: поздняя комната может
затереть единственный проход к ранней. Альтернатива — перегенерировать этаж целиком — делает
время генерации неограниченным. Тест `MapGen.EveryWalkableCellIsReachableFromTheEntrance`
проверяет инвариант на 300 зёрнах.

### Симметричное теневое литьё

Первая версия использовала классическое рекурсивное теневое литьё. Оно быстрое и на глаз
правильное, но несимметричное: находились клетки, откуда монстру видно героя, а герою монстра —
нет. В игре, где Аспид плюётся ядом на расстоянии, это читается как жульничество.

Тест `Fov.IsSymmetricOnOpenTerrain` (для каждой видимой клетки проверить, что из неё видно
источник) поймал это на первом же прогоне. Алгоритм заменён на симметричную формулировку
Альберта Форда: клетка пола освещается, только если её центр попал внутрь видимого клина, а
стены — если клин их вообще коснулся. Стены остаются сплошными, а видимость между клетками пола
становится симметричным отношением.

### Карта потоков вместо A\* на каждого монстра

Первая версия гоняла A\* для каждого монстра каждый ход. На нижних этажах с двумя десятками
тварей это доминировало в профиле.

Сейчас раз за такт строится карта Дейкстры от героя — расстояние в шагах до него из каждой
клетки. Спуск по этой карте — погоня, подъём — бегство. Одно построение обслуживает всех.
A\* остался запасным вариантом на случай, когда поле заблокировано другим монстром в узком
коридоре.

### Двуязычность внутри движка

Каждая строка, которую видит игрок, — это `Text` с двумя полями: `ru` и `en`. Записи журнала
хранят оба варианта, а не заранее отрендеренную строку.

Это позволяет переключить язык в любой момент, включая уже написанные сообщения. Цена — лишняя
строка на запись; выигрыш — язык не приходится решать в момент, когда сообщение создаётся.

### Формат сохранения

Версия формата — 10. Старые версии не читаются: миграции нет, и сохранение прежней версии
отклоняется целиком, а не загружается как что-то другое. Для игры, которая не обновляется у
игроков, это честнее миграции, написанной наугад; для живого проекта пришлось бы дописывать.
Версия росла вместе с состоянием: 4 — залы стражей, 5 — огонь Огневика, 6 — строки бестиария, 7 — счётчики достижений, 8 — проклятые вещи, 9 — события этажа, 10 — «последний страж не тронул».


Текстовые токены через пробел с версией в заголовке. Сетки тайлов и разведанности сжаты RLE.

Почему не бинарный формат: сохранение можно открыть и прочитать глазами, оно нормально ложится
в `localStorage` и не зависит от порядка байт. Этаж 72×34 занимает около 2 КБ, вся партия из
шестнадцати этажей — единицы килобайт.

Загрузка строгая. Всё разбирается во временный `Game`, и только полностью успешный разбор
подменяет живой объект. Это значит, что обрезанное или подделанное сохранение не может оставить
движок в полусобранном состоянии. Проверяются: версия формата, границы глубины, размеры карты,
диапазоны типов тайлов и видов существ, количество элементов (чтобы враждебное сохранение не
заявило миллиард монстров и не исчерпало память до всякой проверки), согласованность индексов
экипировки с содержимым котомки и координаты — героя, каждого существа и каждого предмета на
полу.

Координаты добавились в этот список последними, и по показательной причине. Выйти за границы
карты здесь не опасно: `Map` за пределами сетки отвечает «стена», так что герой на клетке
(9999, −9999) ничего не портит — он просто оказывается в углу ничего, куда не дойдёт ни одна
тварь и где не будет лестницы. Именно поэтому проверка и нужна: это не падение, которое видно
сразу, а партия, которая продолжается и не может кончиться. Проверяются только границы, не
проходимость: герой законно стоит и в воде, и в дверях, и правило строже игровского начало бы
отбраковывать честные сохранения.

## Слой WebAssembly

`frontend/web/bindings.cpp` — тонкая C-обёртка. JavaScript шлёт действия целыми числами и
получает состояние одним JSON-документом на ход.

Карта передаётся не массивом объектов-клеток, а тремя параллельными строками плюс маленькая
палитра цветов:

```json
{ "map": { "glyphs": "..####...", "colors": "AABBCC...", "vis": "012...", "palette": ["#7d6c58", ...],
           "terrain": "AABBB...", "terrainKeys": ["wall", "floor", ...],
           "entities": "  C  A ", "entityKeys": ["upyr", "item_gold", ...] } }
```

Этаж — это 2448 клеток. Объект на клетку превращал ход примерно в 300 КБ JSON, что заметно на
телефоне. Пять строк и три коротких словаря дают около 12 КБ.

`glyphs`/`colors` и `terrain`/`entities` описывают один и тот же кадр двумя способами, поэтому
страница переключается между символьным и спрайтовым рендером, не спрашивая у движка другой
кадр.

Сборка идёт с `-sSINGLE_FILE=1`: бинарь WebAssembly встроен в `nav.js` как data-URI. Получаются
ровно два файла, которые кладутся на любой статический хостинг без настройки MIME-типов.

## Фазы боссов

`Species::phases` — сколько рисунков у существа; всё обычное имеет один. Фаза живёт на
монстре (`Monster::phase`) и пересчитывается в `update_boss_phase`, который вызывается из
`damage_monster` — то есть из единственного места, через которое проходит любой урон.

Пороги — ровные доли полоски здоровья, а не подобранные числа: босса потом перебалансируют,
и подобранное число тихо съест одну из фаз. Фаза только растёт — иначе лечение вернуло бы
игроку рисунок, который он уже разгадал, и бой превратился бы из трудного в нудный. На
переходе сбрасываются счётчики телеграфов: заряд, набранный по старым правилам, выстрелил бы
по новым, а с той стороны экрана это читается как жульничество.

## Перекрёсток

Глубина 0 — единственный этаж, который ничем не порождается. `build_lobby` кладёт стены,
вырезает комнату, ставит капище, лестницу и три постамента. Нечисти нет; `populate` туда не
заходит.

Правило «берут одно» живёт не во флаге на предмете, а в `act_pick_up`: если герой на
перекрёстке и после подбора на полу что-то осталось — остальное убирается. Флаг на предмете
пришлось бы протаскивать через сохранение и через все проверки загрузки ради одной комнаты.

## Снаряжение с механикой

`GearTemplate` носит битовую маску `GearPower` и номер набора. Биты, а не перечисление,
потому что у одной вещи их может быть два — наузы держат и яд, и огонь. `Game::hero_powers()`
складывает маски трёх надетых вещей, `hero_set()` возвращает набор, только если все три из
одного.

Три предмета на три слота — не совпадение: собранный набор занимает героя целиком, и это
делает его решением про весь спуск, а не про руку. Каждый предмет при этом работает и в
одиночку; набор, бесполезный до последней вещи, — ловушка, и отдельный тест это запрещает.

Вопрос «пристаёт ли к герою этот эффект» вынесен в `hero_resists` и задаётся обоими путями,
которыми эффект может прийти. Пока их было два, они разошлись — см. NAV-010.

## Графика

Спрайты не хранятся картинками. `tools/sprites/pixels.py` — это пятьдесят пять рисунков 16×16,
записанный текстом: шестнадцать строк на спрайт, точка — прозрачность, остальные знаки —
ключи в палитру самого спрайта. Причина простая: изменённый пиксель должен быть виден в diff'е
как изменённый символ, а не как «binary files differ». `tools/sprites/build.py` собирает из
этого `frontend/web/sprites.js` — палитра и 256 знаков на спрайт, около 35 КБ на всю игру, —
и контактный лист `docs/media/sprites.png` для глаз.

Движок про пиксели не знает: `RenderCell` отдаёт `terrain` и `entity` — стабильные строковые
ключи («wall», «upyr», «hero_vityaz»). Ключи именно строки, а не значения перечисления:
фронтенд, завязанный на числа, начнёт молча рисовать не то в день, когда в перечисление
добавят элемент, а отсутствующий строковый ключ ловит `test_sprites.cpp`.

Разделение земли и того, кто на ней стоит, — не украшение: пока клетка описывалась одним
символом, монстр на лестнице стирал лестницу. Теперь это два слоя, и рисуются они друг
поверх друга.

Тайлы нарисованы нейтрально-серыми и подкрашиваются на лету цветом текущего пояса. Цвет
нормализуется до полной яркости и умножается на серый — так сохраняется светотень рисунка и
меняется только тон. Иначе понадобилось бы три копии каждого тайла и три возможности забыть
про одну из них.

## Что можно было бы сделать иначе

**ECS вместо структур.** Для игры такого размера entity-component-system добавил бы больше
церемоний, чем гибкости: сущностей два вида (герой и монстр), и у них почти одинаковый набор
полей.

**Скриптовый язык для контента.** Lua позволил бы менять баланс без пересборки. Но тогда
контент перестал бы проверяться компилятором и `GameData.TablesAreInternallyConsistent`
пришлось бы писать заново на другом уровне. При текущем объёме контента таблицы в C++ выигрывают.

**Мультиплеер.** Детерминированное ядро с состоянием, полностью укладывающимся в сохранение,
для этого подходит хорошо: по сети достаточно гонять зерно и список действий. Это самое
очевидное направление развития.
