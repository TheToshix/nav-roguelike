# Архитектура

Документ описывает, как устроен проект и почему он устроен именно так.

---

## Главное решение: ядро без ввода-вывода

Всё, что относится к правилам игры, лежит в `engine/` и не делает ни одного вызова
ввода-вывода. Ни `printf`, ни чтения клавиш, ни работы с файлами. Наружу торчит один класс:

```cpp
class Game {
public:
    void start(const GameConfig& cfg);
    bool perform(const Action& action);   // true, если ход был потрачен

    const Map& map() const;
    const Hero& hero() const;
    const std::vector<Monster>& monsters() const;
    const std::vector<LogEntry>& log() const;
    RenderCell render_at(Vec2 p) const;

    std::string save() const;
    bool load(const std::string& blob);
};
```

Фронтенд присылает `Action` и читает состояние обратно. Больше между ними ничего нет.

Из этого следуют три вещи, ради которых всё и затевалось:

1. **Правила проверяются тестами без экрана.** Тест создаёт `Game`, ставит героя куда нужно,
   выдаёт `Action` и смотрит на результат. Никаких моков терминала.
2. **Два фронтенда работают с одним кодом.** Терминальная версия и версия для браузера — это
   два разных способа нарисовать одно и то же состояние и превратить нажатие в `Action`.
3. **Сохранение — это сериализация состояния, а не отдельная подсистема.** Всё, что описывает
   партию, уже собрано в одном объекте.

```
                    ┌─────────────────────────────────┐
                    │            engine/              │
                    │                                 │
   Action ────────► │   Game::perform()               │
                    │     ├─ actions.cpp   ход героя  │
                    │     ├─ ai.cpp        ход тварей │
                    │     ├─ game.cpp      очередь    │
                    │     ├─ mapgen.cpp    генерация  │
                    │     ├─ fov.cpp       обзор      │
                    │     ├─ pathfind.cpp  A* и поток │
                    │     ├─ data.cpp      контент    │
                    │     └─ save.cpp      сохранения │
                    │                                 │
   состояние ◄───── │   map() hero() monsters() ...   │
                    └─────────────────────────────────┘
                        ▲             ▲             ▲
                        │             │             │
              ┌─────────┴───┐  ┌──────┴──────┐  ┌───┴──────┐
              │  терминал   │  │   браузер   │  │  тесты   │
              │  ANSI+termios│ │  WASM+canvas│  │GoogleTest│
              └─────────────┘  └─────────────┘  └──────────┘
```

## Из чего состоит движок

| Файл | Отвечает за |
|---|---|
| `rng.hpp` | Детерминированный генератор случайных чисел |
| `geometry.hpp` | `Vec2`, `Rect`, расстояния, восемь направлений |
| `text.hpp` | Двуязычная строка `Text` и подстановка `{}` |
| `types.hpp` | Тайлы, эффекты, виды предметов, `Action`, записи журнала |
| `map.hpp` | Сетка тайлов, видимость, разведанность |
| `mapgen.cpp` | BSP-генерация этажа и ремонт связности |
| `fov.cpp` | Симметричное теневое литьё, линии Брезенхэма |
| `pathfind.cpp` | A\* и карта потоков (Дейкстра) |
| `entity.hpp` | `Actor`, `Monster`, `Hero`, `Inventory` |
| `item.hpp` | Предметы и система опознавания |
| `data.cpp` | Весь контент: бестиарий, снаряжение, зелья, свитки, классы, заклятья |
| `game.cpp` | Жизненный цикл, этажи, очередь ходов, производные характеристики |
| `actions.cpp` | Действия героя, модель урона, прогрессия |
| `ai.cpp` | Поведение монстров |
| `save.cpp` | Сериализация и строгая загрузка |

Весь контент собран в одном `data.cpp` намеренно: баланс игры видно в одном диффе, а код
правил остаётся свободным от магических чисел.

## Ключевые решения и их причины

### Свой генератор случайных чисел

`std::mt19937` переносим, но `std::uniform_int_distribution` — нет: одна и та же
последовательность даёт разные числа в libstdc++, libc++ и MSVC. Для игры, где зерно должно
задавать подземелье одинаково на всех платформах и в браузере, это неприемлемо.

Используется xoshiro256\*\* с посевом через splitmix64 и выборкой с отбраковкой (rejection
sampling), чтобы распределение было ровно равномерным, а не смещённым, как при `% n`.
Состояние генератора входит в сохранение — иначе загруженная партия разошлась бы с исходной.

### Очередь ходов по энергии

У каждого существа есть скорость и накопленная энергия. За такт все получают энергию, равную
своей скорости, и действуют, пока её хватает на ход (100 единиц). Витязь со скоростью 100
ходит раз за такт, Волколак со скоростью 130 — примерно 1,3 раза, а Каменная баба со
скоростью 70 — 0,7.

Это даёт бесплатно: эффекты ускорения и замедления, разную стоимость действий (вода стоит
полтора хода) и возможность оглушить существо, просто не дав ему потратить энергию.

Цикл ограничен сверху: если бы планировщик когда-нибудь зациклился, это проявится как
падающий тест, а не как зависшая вкладка браузера.

### Генерация этажа с гарантией связности

1. Уровень рекурсивно режется BSP-разбиением на области.
2. В каждом листе вырезается комната случайного размера.
3. Каждый внутренний узел соединяет комнату из левого поддерева с комнатой из правого —
   по построению получается остовное дерево над всеми комнатами.
4. Добавляется несколько лишних коридоров, чтобы этаж не был чистым деревом из тупиков.
5. **Проход ремонта связности**: заливкой ищутся отрезанные области, и к ближайшей достижимой
   клетке пробивается туннель. Цикл ограничен числом областей, поэтому всегда завершается.
6. Расставляются вода, пропасти, двери, капище и лестницы. Пропасти непроходимы, поэтому после
   них ремонт запускается ещё раз.

Пункт 5 существует потому, что шаги 2–4 не дают гарантии сами по себе: поздняя комната может
затереть единственный проход к ранней. Альтернатива — перегенерировать этаж целиком — делает
время генерации неограниченным. Тест `MapGen.EveryWalkableCellIsReachableFromTheEntrance`
проверяет инвариант на 300 зёрнах.

### Симметричное теневое литьё

Первая версия использовала классическое рекурсивное теневое литьё. Оно быстрое и на глаз
правильное, но несимметричное: находились клетки, откуда монстру видно героя, а герою монстра —
нет. В игре, где Аспид плюётся ядом на расстоянии, это читается как жульничество.

Тест `Fov.IsSymmetricOnOpenTerrain` (для каждой видимой клетки проверить, что из неё видно
источник) поймал это на первом же прогоне. Алгоритм заменён на симметричную формулировку
Альберта Форда: клетка пола освещается, только если её центр попал внутрь видимого клина, а
стены — если клин их вообще коснулся. Стены остаются сплошными, а видимость между клетками пола
становится симметричным отношением.

### Карта потоков вместо A\* на каждого монстра

Первая версия гоняла A\* для каждого монстра каждый ход. На нижних этажах с двумя десятками
тварей это доминировало в профиле.

Сейчас раз за такт строится карта Дейкстры от героя — расстояние в шагах до него из каждой
клетки. Спуск по этой карте — погоня, подъём — бегство. Одно построение обслуживает всех.
A\* остался запасным вариантом на случай, когда поле заблокировано другим монстром в узком
коридоре.

### Двуязычность внутри движка

Каждая строка, которую видит игрок, — это `Text` с двумя полями: `ru` и `en`. Записи журнала
хранят оба варианта, а не заранее отрендеренную строку.

Это позволяет переключить язык в любой момент, включая уже написанные сообщения. Цена — лишняя
строка на запись; выигрыш — язык не приходится решать в момент, когда сообщение создаётся.

### Формат сохранения

Текстовые токены через пробел с версией в заголовке. Сетки тайлов и разведанности сжаты RLE.

Почему не бинарный формат: сохранение можно открыть и прочитать глазами, оно нормально ложится
в `localStorage` и не зависит от порядка байт. Этаж 72×34 занимает около 2 КБ, вся партия из
двенадцати этажей — единицы килобайт.

Загрузка строгая. Всё разбирается во временный `Game`, и только полностью успешный разбор
подменяет живой объект. Это значит, что обрезанное или подделанное сохранение не может оставить
движок в полусобранном состоянии. Проверяются: версия формата, границы глубины, размеры карты,
диапазоны типов тайлов и видов существ, количество элементов (чтобы враждебное сохранение не
заявило миллиард монстров и не исчерпало память до всякой проверки) и согласованность индексов
экипировки с содержимым котомки.

## Слой WebAssembly

`frontend/web/bindings.cpp` — тонкая C-обёртка. JavaScript шлёт действия целыми числами и
получает состояние одним JSON-документом на ход.

Карта передаётся не массивом объектов-клеток, а тремя параллельными строками плюс маленькая
палитра цветов:

```json
{ "map": { "glyphs": "..####...", "colors": "AABBCC...", "vis": "012...", "palette": ["#7d6c58", ...] } }
```

Этаж — это 2448 клеток. Объект на клетку превращал ход примерно в 300 КБ JSON, что заметно на
телефоне. Три строки и палитра дают около 8,5 КБ.

Сборка идёт с `-sSINGLE_FILE=1`: бинарь WebAssembly встроен в `nav.js` как data-URI. Получаются
ровно два файла, которые кладутся на любой статический хостинг без настройки MIME-типов.

## Что можно было бы сделать иначе

**ECS вместо структур.** Для игры такого размера entity-component-system добавил бы больше
церемоний, чем гибкости: сущностей два вида (герой и монстр), и у них почти одинаковый набор
полей.

**Скриптовый язык для контента.** Lua позволил бы менять баланс без пересборки. Но тогда
контент перестал бы проверяться компилятором и `GameData.TablesAreInternallyConsistent`
пришлось бы писать заново на другом уровне. При текущем объёме контента таблицы в C++ выигрывают.

**Мультиплеер.** Детерминированное ядро с состоянием, полностью укладывающимся в сохранение,
для этого подходит хорошо: по сети достаточно гонять зерно и список действий. Это самое
очевидное направление развития.
